## SQL vs. Python Optimization Plan

### Analysis: What Can Move to SQL

The current notebook pulls **all raw rows** (~2.4M) into Python, then does groupby aggregation and rate computation in pandas. This is the primary bottleneck — the aggregation and rate computation are pure SQL operations.

---

### Steps to Move to SQL (Sections 3–4)

**Replace**: `SELECT *` → `pd.groupby().sum()` → `compute_rates()` in Python  
**With**: A single SQL query per dimension that does the GROUP BY + rate computation in Snowflake, returning only the aggregated profiles (~thousands of rows instead of millions).

**SQL query pattern** (one per dimension):

```sql
-- Example for fin_market dimension
SELECT
    fin_market,
    hce_admit_month,
    SUM(case_count) AS case_count,
    SUM(initial_adr_cnt) AS initial_adr_cnt,
    SUM(persistent_adr_cnt) AS persistent_adr_cnt,
    SUM(md_reviewed_cnt) AS md_reviewed_cnt,
    SUM(p2p_case_cnt) AS p2p_case_cnt,
    SUM(p2p_ovrtn_case_cnt) AS p2p_ovrtn_case_cnt,
    SUM(member_appeal_cnt) AS member_appeal_cnt,
    SUM(member_appeal_ovtn_cnt) AS member_appeal_ovtn_cnt,
    SUM(mcr_reconsideration_case_cnt) AS mcr_reconsideration_case_cnt,
    SUM(mcr_ovrtn_case_cnt) AS mcr_ovrtn_case_cnt,
    SUM(pre_auth_cases) AS pre_auth_cases,
    SUM(membership) AS membership,
    SUM(days) AS days,
    SUM(admits) AS admits,
    SUM(allowed) AS allowed,
    SUM(netpaid) AS netpaid,
    -- Computed rates (Snowflake handles NULLIF natively)
    SUM(persistent_adr_cnt) / NULLIF(SUM(case_count), 0) AS persistent_adr_rate,
    SUM(initial_adr_cnt) / NULLIF(SUM(case_count), 0) AS initial_adr_rate,
    SUM(member_appeal_ovtn_cnt) / NULLIF(SUM(initial_adr_cnt), 0) AS member_appeal_overturn_rate,
    SUM(p2p_ovrtn_case_cnt) / NULLIF(SUM(initial_adr_cnt), 0) AS p2p_overturn_rate,
    SUM(member_appeal_cnt) / NULLIF(SUM(initial_adr_cnt), 0) AS member_appeal_rate,
    SUM(p2p_case_cnt) / NULLIF(SUM(initial_adr_cnt), 0) AS p2p_rate,
    SUM(case_count) * 12000.0 / NULLIF(SUM(membership), 0) AS auth_per_k
FROM tmp_1m.kn_loc_notif_05062026_od
WHERE ipa_pac_flag IN ('IPA', 'MM')
    AND loc_flag = 1
    AND mnr_total_ffs_flag = 1
    AND hce_admit_month BETWEEN '202501' AND '202605'
GROUP BY fin_market, hce_admit_month
HAVING SUM(case_count) >= 15
```

Repeat for `hospital_group` and `prov_tin`.

### What STAYS in Python (Sections 5–9)

| Section | Reason to keep in Python |
|---------|--------------------------|
| **5. Cross-sectional MAD z-scores** | MAD computation with per-group iteration, conditional logic (`if len(vals) < 5`), and dynamic column creation — awkward in SQL window functions for this use case |
| **6. MoM rolling z-scores** | Entity-level rolling window with `shift(1)`, eligibility filtering (≥6 months), per-entity iteration — better suited to pandas |
| **7. Combined scoring** | Merge + boolean logic on small dataframes (already aggregated) |
| **8. Feature-level deep dive** | Iterative display/reporting logic |
| **9. Distribution profiling** | matplotlib histograms, seaborn heatmaps, skew/sparsity stats |

2. **Remove cell-10** (Python `groupby` + `compute_rates` function)

### Performance Impact

- **Current**: Pull 2.4M rows × 80 columns → pandas groupby × 3 dimensions = ~30–60s data transfer + memory pressure
- **After**: 3 queries each returning ~1K–5K rows × 25 columns = ~2–5s total, negligible memory

### Refactored Section 4 Pseudocode

```python
PROFILE_SQL = """
SELECT {dim}, hce_admit_month,
       SUM(case_count) AS case_count, ...all count cols...,
       -- all 7 rate computations --
FROM {SOURCE_TABLE}
WHERE ipa_pac_flag IN ('IPA', 'MM') AND loc_flag = 1 AND mnr_total_ffs_flag = 1
    AND hce_admit_month BETWEEN '202501' AND '202605'
GROUP BY {dim}, hce_admit_month
HAVING SUM(case_count) >= {MIN_CASES}
"""

monthly_profiles = {}
for dim in DIMENSIONS:
    monthly_profiles[dim] = pd.read_sql(PROFILE_SQL.format(dim=dim, ...), engine)
```
